The Problem

Rebranding a design system is a search-and-replace job, and it shouldn't be

Most systems bake their brand into their components. A colour lives in a Button, a tint lives in a Badge, a hex sits in a slide template. When the brand changes — a rebrand, a client project, a white-label build — someone has to find every one of those and hope they got them all. The work is tedious, invisible when it goes right, and embarrassing when it doesn't.

I wanted to find out what it takes to make that a non-event. The target was deliberately awkward: change one hex value and have it correctly re-derive a 12-step colour ramp, 180+ tokens, every component, three themes, and a 14-slide PowerPoint template — with the accessibility grades still holding at the other end.

The last clause is the hard part. Propagating a colour is easy. Propagating a colour without quietly breaking contrast somewhere is the actual problem, and it's what most of the interesting decisions below are about.

Pillar 03 · Token Cascade

The 3-Layer Token Cascade Architecture

Tokens are organized into three strict abstraction layers to decouple raw hex values from component implementations:

Layer 1: Primitives (Raw Specs)
--brand-500: #10b981;  ·  --neutral-900: #171717;

Layer 2: Semantic Aliases (Intent Rules)
--action-primary: var(--neutral-900);  ·  --surface-default: var(--neutral-0);

Layer 3: Component Implementation
<Button variant="primary"> → consumes var(--action-primary)
Decisions & Trade-offs

Four decisions that shaped the system

Each of these cost something. Listing what I gave up is more useful than listing what I built.

Components address meaning, never a palette step

A button asks for --action-brand, not --brand-600. Themes re-point the alias; the button never learns that a brand exists. This is the single decision the whole system rests on — it's why a brand swap reaches a PowerPoint export without any code in the export path knowing about brands.

The cost: a layer of indirection that makes the system harder to learn. A newcomer reading --action-brand has to go look up what it resolves to. I accepted that because the alternative — components reaching into the palette directly — is exactly the coupling that makes rebranding a search-and-replace job.

OKLCH for the ramp, not HSL

HSL "lightness" is a geometric midpoint of the RGB cube, not a perceptual one. Build a ramp on a fixed HSL lightness ladder and step 600 lands at a very different perceived brightness for amber than for indigo — so brand-coloured text passes contrast for one brand and fails for another, silently, at swap time.

OKLab is constructed so equal steps in L are equal perceived steps at every hue. Moving the engine to it took the spread in "brand-600 against white" across seven test hues from 3.00 down to 1.06, and let me tune the shade rungs so every hue clears WCAG AA.

The cost: out-of-gamut colours. OKLCH can describe colours sRGB can't display, so the engine reduces chroma by binary search at constant lightness and hue rather than clipping per channel — clipping is cheaper but shifts the hue, which shows up as a ramp that drifts colour at its most saturated steps.

Step 500 returns the seed verbatim; every other rung is normalised

There's a real tension here. Anchor every rung to an absolute perceptual lightness and the ramp behaves predictably across brands — but the colour a user typed no longer appears in their own palette, which is baffling in a tool whose entire premise is "your brand seed". Derive every rung from the seed instead and you get the user's colour back, but the contrast guarantees evaporate.

The resolution: pin 500 to the seed exactly, target absolute lightness for everything else, and nudge only as far as needed to keep the ladder monotonic. You get your colour and predictable contrast.

The cost: for an unusually light or dark seed, the rung immediately next to 500 compresses toward it. A pale yellow brand has a tighter 400–500 gap than a mid-tone blue does. That's a visible imperfection I chose over an invisible accessibility regression.

"Paper" is a token, not a colour

--pure-white is not white. It's whichever end of the value range reads as background in the active theme, flipping to near-black under data-theme="dark". Slides carry their own data-theme, so a light slide sitting inside dark chrome resolves its own tints correctly.

The cost: a token named "white" that isn't white is a genuine trap for anyone new to the codebase, and it caused a real bug — see below.

Evidence

The accessibility checker was lying, and finding out fixed three other things

The studio ships a WCAG contrast auditor that grades every text-on-surface token pair. It looked authoritative. It was reporting frozen numbers: each pair stored a hardcoded hex captured from the original emerald light theme, so the panel reported the same ratios no matter which brand or theme was active. An accessibility tool confidently reporting stale data is worse than no tool, because it stops you looking.

Rewriting it to resolve token values from the live cascade at render time surfaced problems in sequence:

Every one of these was a value that had escaped the token layer. The bug wasn't in the checker — the checker was where the bug became visible.

With those fixed, the auditor became worth listening to — and immediately failed the system in two more places, both in themes I'd assumed were fine. All 30 audited pairs now meet AA or better across light, dark, and high-contrast.

That reframed the rest of the audit. Instead of hunting individual rendering glitches, the question became: where else has a literal escaped? That's what turned up a --pure-white that was never declared at :root — so in the default light state every bg-[var(--pure-white)] resolved to an invalid value, giving black text on black buttons and an export modal with no background. One missing declaration, three unrelated-looking symptoms.

Accessibility

The system documented a focus token it never used

--focus-ring was defined in all three themes and listed in the studio's own Token Map as "Focus outline". It was applied to nothing. There was not a single :focus rule in the codebase. Keyboard users got the browser's default blue — a colour from outside the system, invisible on some surfaces, and absent entirely on the search field, which carried an inline outline: none.

Fixing it properly meant more than adding a rule. Inline styles beat any selector, so eleven inline outline: none declarations had to go. A zero-specificity :where() selector loses to a single utility class, so the rule uses element selectors. And Tailwind's transition-colors animates outline-color, which faded the indicator in over 150ms — a focus ring has to be instant, so the rule opts out of transitions.

The system now also honours prefers-reduced-motion, ships a skip link, and has an accessible name on every interactive control in both apps.

What I'd Do Next

Where this still falls short

Being specific about the gaps is more credible than claiming there aren't any.

The contrast rule is duplicated

The OKLCH engine exists twice — once as a browser global for the studio, once as a TypeScript module for the bundled generator. They're verified byte-identical by a parity check, but a shared package would be the honest fix.

Contrast isn't enforced, only reported

The auditor tells you a pair fails. It should be able to refuse a seed that can't produce an accessible ramp, or auto-suggest the nearest one that can.

The deck editor is desktop-only

Below 720px it explains itself and offers a read-only preview rather than pretending to work. That's honest, not solved — a genuine touch editing model is a separate project.

No regression tests on the token layer

Every contrast figure here was measured by hand. Those measurements should be a test that fails the build when a seed stops clearing AA.
